# X 社区运营工作台（X Community Ops Hub）

面向 X（Twitter）创作者与社区运营者的**Java 服务端 + 内嵌 X 原生风前端**。系统实行**「X 官方授权登录 · 每人仅查本人账号 · 当天数据按小时核验」**机制，登录后可按 **24小时 / 48小时 / 7天 / 30天** 四个周期一键切换查看本人 5 大核心社区运营模块：

1. **发帖与回复活跃度看板**：支持按月（30天单日趋势）、按周（7天星期趋势）、按48小时（逐时节奏）查看原创发帖、主动暖场回复、引用/转推构成、回复/发帖比、主推平均公开互动率（ER%）与运营健康分。
2. **推友双向互动率深度拆解**：一对一拆解与全量排行榜联动，直观对比「我去评论 : 他来评论」、「引用比」、「@提及比」、「对方互动回礼率（对方互动 ÷ 我方互动）」与「社交精力占比」，自动分层 `双向奔赴` / `铁粉主动捧场` / `我方主动暖场`。
3. **未回关关注关系体检**：比对关注与粉丝名单，筛出「我关注但未回关」、「关注我但我未回关」、「互关推友」；叠加当前周期互动频次智能识别 **高粉大V防误删（≥2.5万粉）**、**我去互动仍未回关**、**普通号零回访建议清理**，支持 CSV 导出与一键直达主页管理。
4. **黄金发帖时段与爆款内容诊断**：按服务端时区（默认北京时间）的星期×时段（7×8）互动率热力图、个人黄金发帖档期 Top 3、短推/图文视频/长推 Thread 体裁转化对比、高影响力推文复盘流。
5. **社区铁粉圈层与晒单战报卡**：自动提炼「核心铁粉圈（Core Yappers）」、「待回访固粉清单（防冷落提醒）」与「活跃互暖伙伴」，支持随维度一键导出 **30天 / 7天 / 48小时战报** 高清 PNG 战报图与发推文案。

## 访问限制与当天数据刷新

- **登录授权且仅限本人查询**：`xops.require-login-self-only` 默认为 `true`。未登录请求 `/api/analyze` 返回 `401`；已登录用户仅可查询自己 OAuth 绑定的账号，用户名参数越权返回 `403`；账号归属以稳定用户 ID 校验，同名不同 ID 的数据不返回、不合并。缓存、使用状态和浏览器白名单按 ID 隔离，新持久化目录为 `users/by-id/<用户ID>/`；旧用户名目录仅经 ID 和用户名校验后复用。用户名已变更时明确阻断，需确认账号并迁移旧用户名历史，不自动合并。
- **当天刷新**　打开或刷新实时报表、点击“检查更新”或切换周期，页面都会向服务端检查本账号已入库的数据。服务端显示快照时间、最近一次完整更新时间、本人动态及入站互动的覆盖情况和待更新指标数。滚动 24 小时的两条数据流均已覆盖、窗口内帖子指标均已核验时，一小时内复用这批数据。到期或首次读取旧缓存时，从上次位置补入新动态和互动，同时按帖子 ID 更新赞、评、转发、书签和浏览数。页面会在同一账号、同一周期内接着读取有进展的批次，每次操作最多 20 批。如上游没有进展或本批失败，会保留已入库的进度；已尝试但未返回的帖子显示为本轮暂不可得，下个小时再查。已覆盖的旧时段仍可能有漏帖，热更新另用 Latest 搜索轮换抽查最近一天的一个 6 小时时段，每轮最多一页。
- **覆盖范围与名单完整性**：TwitterAPI.io 的时间线和提及流均覆盖目标时间，才算该窗口完成；上游分页、超时或预算限制导致未完成时，保留已有数据和游标，不把缺口当作已覆盖。重复游标、缺少结果数组和无效日期不代表取完；短时间缺口也保留，只有新增覆盖才算继续取得进展。单个流或分片失败时，已成功且日期有效的在途页面仍保存其覆盖，避免丢失已付费进度；降级状态继续阻止本批发起新的页面请求。官方 X API 当前只采集有界首屏快照，覆盖范围以实际取得的时间段为准。明确覆盖为 0 天时保留 0，不按请求窗口填成完整。关注与粉丝名单分别记录是否完整；分页结束但名单唯一数量与账号计数不一致，也按完整性存疑处理。TwitterAPI.io 普通粉丝分页成功结束但人数不足时，会在原同步时限内额外取一次粉丝 ID 列表，并仅补查最多 20 个缺失 ID 的资料；仅当 ID 列表已结束、唯一数量与资料总数一致且最终身份集合完全相等时才标为完整。两次补采均为有界付费读取，无额外重试；不可用身份、接口错误或未完成继续保留缺口。名单仍存疑时，TwitterAPI.io 会对关注名单中未出现在粉丝结果的对象补查双方关系；明确结果可正常归为互关、未回关或粉丝关系，只有无法确认的对象保留未知。关注名单完整且其中所有关系均已确认时，回关率可为完整结果，同时继续提示总粉丝名单的缺口。
- **逐人关系核验**：读取 `check_follow_relationship`，`source_user_name` 为本人、`target_user_name` 为对方；只接受成功响应中的布尔 `following`（本人关注对方）与 `followed_by`（对方关注本人）。每次同步最多 100 个候选、最多 4 个并发，遵守现有共享限流与同步时限；不自动重试。接口按人计费，目前公开标价每次 100 credits；时间或额度限制、错误及缺字段仍为未知，不据此建议清理。证据记录稳定 ID 和核验时间，构造新快照时超过 300 秒不再作为已核实关系；新图谱刷新或失败降级清除旧证据，同图谱扩窗可复用。未核验对象超过单批限制时，点击“继续核验关系（N）”只补一批，不自动循环；名单过期或身份变化时需先刷新。实际请求的尝试时间单独保存用于轮转，失败对象不会永远占住前 100 位，也不把尝试记录当作关注证据。关系状态是查询时点事实，非永久保证。[接口契约与价格](https://docs.twitterapi.io/api-reference/endpoint/check_follow_relationship)
- **指标新鲜度**：报表窗口以资料快照为固定终点；续传过程中，指标按各批响应接收时间记录，读数可能晚于窗口终点。页面“指标最近采集”只表示最近 24 小时窗口中有可靠采集时间的成功指标的最近一次读数，不代表全部指标在同一时刻测量；旧缓存无法确认实际读数时间时显示未确认。当天按 ID 补读每批最多 50 条，24 小时以外的历史指标保留上次实测时间。历史推文指标每次热更新最多同步 1 批、每批最多 50 条；按最近尝试时间轮转，同龄记录优先补齐缺指标的独立主推和引用，串推楼层不冒充独立主推。指标批读取只尝试一次，必须在本轮原同步软截止点前获准发出（排队后会再次检查）；获准后，当天指标批读取最多等待 25 秒，历史指标批最多等待 15 秒。已过截止点不发请求，上游失败仍保留旧已知值及未知状态。未同步的历史指标仍是采集时快照，互动率、排行和浏览数不代表全量实时数据。时间线与提及流采集不完整、名单采样或指标更新受限时，应结合报表提示解读。
- **缺失指标与旧缓存**：缺失的浏览、赞、回复、转推/引用、书签与真实 0 分开记录；按所需字段已知的样本计算均值和互动率，并披露样本数。浏览为 0 时不能计算互动率，显示 `--`；无可用样本不评分或推荐黄金时段。刷新只更新返回的字段，不用缺失字段覆盖已有测量。旧记录没有可用性元信息时保守视为未知，等待后续刷新补充；不删除旧数值，也不把它们冒称为已验证指标。该说明同步用于页面、复制、分享链接和 PNG。
- **主帖访问与时间桶**：只有根帖归属证据明确的回复才计入“我去评 TA 主帖／TA 来评我主帖”；楼中楼及旧记录缺少归属字段时不作肯定推断，原始回复活动数仍保留。48 小时统计以滚动起点划分 48 个小时桶，趋势图为同一起点的 24 个两小时桶，最后一桶包含窗口终点。
- **查看已入库报表**：登录后可从顶栏打开最近一次入库的本人报表。页面显示原采集时间，24 小时、48 小时、7 天和 30 天按同一入库快照计算。趋势图上方列出本周期非纯转推的总浏览、总互动及各自的已知样本数。点击“返回实时报表”可继续正常同步。
- **趋势图串推口径**：原创/引用柱包含串推楼层，明细单列楼层数并计入总动态，与浏览等指标的样本范围一致；主推原创数与回复数的业务定义不变。
- **部分样本的业务建议**：日均按实际已覆盖时长折算，并明确不是完整周期的真实整日结果。引用、提及及未能确认根帖归属的对话不冒充主帖互评，但会阻止“完全零互动”的错误清理建议。历史覆盖不足时暂停按零互动/单向付出建议取关。待回访包含尚未回应的评论；核心铁粉、活跃互暖和待回访是不同维度，可有重叠，三组都在战报页显示。
- **指标解释与隐私**：公开互动率使用公开赞、评、转推/引用、书签与浏览数计算，不等同于官方 Analytics Engagement rate。运营分、内容提示及 1–3% 参考区间属于本站启发式，不证明 For You 来源、影子封禁、平台权重或外链因果。隐藏回关率同时作用于图片、复制文案和发推链接，包含样本回关率及其附注。
- **关系操作状态**：点击“去取关／去回关／关注作者”只打开外部页面，不代表操作完成，不减少待办；以之后刷新取得的关系证据确认。旧版点击产生的乐观关注或本地已处理标记不再作为完成证据。
- **官方 API 契约**：请求按当前文档使用 `post.fields` 和 `referenced_posts` 扩展，解析兼容新旧帖子引用、扩展集合及计数字段。该兼容性有本地契约测试，仍不代表已验证真实官方端点的权限或现网行为。[官方帖子接口文档](https://docs.x.com/x-api/users/get-posts)
- **时区**：`xops.timezone`（环境变量 `X_TIMEZONE`）默认为 `Asia/Shanghai`。时段标签、当前黄金档与等待时间使用后端返回的同一时区。

## 配置文件说明（`src/main/resources/application.yml`）

密钥通过环境变量或项目根目录的私密 `application-local.yml` 配置，前端不暴露任何 API Key 输入框。`src/main/resources/application.yml` 的凭据默认值为空，不包含本机密钥。

1. **配置 X OAuth 2.0 登录授权（必配以开放用户登录与图文定时发布）**
   前往 [X Developer Portal](https://developer.x.com/en/portal/dashboard) 创建项目与应用，开启 **User authentication settings -> OAuth 2.0**：
   - App permissions：`Read and write`（默认登录仅申请最小只读范围 `users.read tweet.read`，浏览器与服务端加密会话保持最长 `400d` 滑动续期；使用模块 6 图文定时发布与逾期二次确认补发时，再通过 `/api/auth/x/authorize-publish` 按需二次授权 `tweet.write media.write offline.access` 并自动轮换 `refresh_token` 长效续期）
   - Type of App：`Web App, Automated App or Bot`
   - Callback URI / Redirect URL：`http://localhost:8080/api/auth/x/callback`（公网部署填 `https://你的域名/api/auth/x/callback`）
   - 若此前已在旧版 `Read` 权限下登录过，升级为 `Read and write` 后只需在页面「定时发布」页签点击「前往 X 二次授权」一次即可，无需退出当前登录；本地会持久化加密读写与离线刷新令牌。
   - 将 TwitterAPI.io Key、**Client ID** 与 **Client Secret** 通过对应环境变量提供，或写入根目录 `application-local.yml`（定时发布相关可选配置见下方）：
     ```yaml
     xops:
       twitterapi-io-key: "${X_TWITTERAPI_IO_KEY:你的_TwitterAPI_io_Key}"
       oauth-client-id: "${X_OAUTH_CLIENT_ID:你的_X_OAuth2_Client_ID}"
       oauth-client-secret: "${X_OAUTH_CLIENT_SECRET:你的_X_OAuth2_Client_Secret}"
       # 可选：自定义本地 OAuth Token AES-GCM 加密密钥（强烈建议生产/持久化环境配置）
       token-encryption-secret: "${X_TOKEN_ENCRYPTION_SECRET:}"
       # 可选：是否启用后台定时发布调度器（默认 true）与宽限窗口秒数（默认 300 秒）
       scheduler-enabled: "${X_SCHEDULER_ENABLED:true}"
       schedule-grace-window-seconds: "${X_SCHEDULE_GRACE_WINDOW_SECONDS:300}"
     ```

   `application-local.yml` 已加入 `.gitignore`，权限应设为 `0600`；它位于项目根目录，不在 Maven 的资源打包目录内，不会自动进入新构建的 JAR。classpath 配置通过 `spring.config.import=optional:file:./application-local.yml` 从**启动进程的工作目录**读取它。部署时可将私密文件放在实际运行目录，或仅配置 `X_TWITTERAPI_IO_KEY`、`X_OAUTH_CLIENT_ID`、`X_OAUTH_CLIENT_SECRET` 环境变量；环境变量仍可覆盖文件里的默认值。不要将私密文件提交或复制到 `src/main/resources`。此配置修复不会修改已存在的 JAR。

2. **打包、测试与启动**

   构建使用 JDK 17 和 Maven，前端回归测试使用 Node.js。本次验证使用 Maven 3.9.12 和 Node.js 24。先运行 `mvn -version`，确认 Maven 使用 Java 17。

   在仓库根目录运行全部 Java 测试并打包，再运行前端回归脚本：

   ```bash
   mvn package
   node src/test/js/auth-state-regression.cjs
   ```

   首次启动可使用演示数据源，检查服务与登录页面。下面的命令适用于 macOS 或 Linux：

   ```bash
   X_PROVIDER=DEMO java -jar target/x-community-hub.jar
   ```

   打开 <http://localhost:8080> 查看页面。健康检查地址是 <http://localhost:8080/api/health>。如果端口已占用，可在启动命令前加 `PORT=8081` 并访问新端口。演示模式保留默认的本人登录限制。

   使用真实账号时，先完成上面的 OAuth 和数据源密钥配置，再运行 `java -jar target/x-community-hub.jar`。默认数据源为 TwitterAPI.io，缺少其密钥时，健康接口会返回 HTTP 400 并提示配置密钥。

   不要在运行中的 JAR 路径上覆盖打包产物。重新打包前先正常停止对应实例，或将新包复制到 `.local/runtime/` 下独立版本路径后运行；启动工作目录仍保持项目根目录，以复用本地配置、会话和缓存。
